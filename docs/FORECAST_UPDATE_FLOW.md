# Forecast Update Flow — actual code path, 2026-09-30 (Phase 4, updated Phase 4.5)

This describes what the code actually does, traced by reading it, not the intended architecture.

**Phase 4.5 update**: items 5 and 11 below are updated from Phase 4's original text to reflect the atomic-write and GFS max-age-gate changes made this phase. The "Remaining blockers" section at the end has been replaced with the Phase 4.5 status of each item.

## `update_grid.yml` (pan-India, 992-cell grid)

1. **Trigger**: cron `30 4,10,16,22 * * *` UTC (4x/day, ~15 min after each GFS cycle posts) + manual `workflow_dispatch`.
2. **Source data fetched**: `backend/pipeline.py` downloads one GFS 0.25° GRIB2 subset (India bbox) from `https://nomads.ncep.noaa.gov/cgi-bin/filter_gfs_0p25.pl` for one resolved `(cycle, fhour)`.
3. **Source data timestamp**: the GRIB2 file itself carries the cycle/fhour in its filename (`gfs.t{cycle}z.pgrb2.0p25.f{fhour:03d}`); `backend/pipeline.py` records `gfs_cycle`/`gfs_fhour`/`generated_at_utc` into the output JSON, but the GRIB2 download itself is written to a `tempfile.TemporaryDirectory()` and deleted after parsing — there is no separately-persisted raw download artifact or a `fetched_at` timestamp distinct from `generated_at_utc`.
4. **Forecast files generated**: `data/pan_india_grid.json` (992 cells, TS/CB/FF hazard probabilities), `data/ctt_grid.json` (cold-cloud-top grid, used for next run's CTT drop-rate).
5. **Script generating each artifact**: `backend/pipeline.py` writes both `pan_india_grid.json` and `ctt_grid.json`. **Phase 4.5**: both writes now go through `atomic_write.py::atomic_write_json()` (temp file in the same directory → flush → fsync → `os.replace()`), replacing the previous direct `OUT_FILE.write_text(json.dumps(...))` / `out_path.write_text(json.dumps(...))`. A failed write (e.g. a NaN sneaking into a hazard field) now leaves the previous valid file completely untouched and exits the job non-zero for the main grid write (a `ctt_grid.json` write failure only warns and continues, since it is next-run drop-rate input, not this run's published forecast).
6. **Canonical script**: `canonical_forecast_writer.py`, invoked as a new step ("Build canonical forecast (Phase 4)") — added this phase, see Part 9 below for the race-mitigation step added immediately before it.
7. **Validation**: schema (`validate_canonical_forecast.py::validate_schema`) + integrity (`validate_integrity`), both called from inside `canonical_forecast_writer.py::main()` **before** any write. No `continue-on-error` on this step — a validation failure stops the job here.
8. **Commit/push**: `git add data/pan_india_grid.json data/ctt_grid.json data/canonical_forecast.json`, commit if changed, push (with rebase-retry on conflict).
9. **Cloudflare deployment**: **none in this workflow.** `update_grid.yml` has no deploy step at all — the pan-India grid update only pushes to `main`; the live site is republished by `forecast_update.yml`'s own, independently-scheduled Cloudflare Pages deploy step, which serves whatever is on `main` at that later time (see Part 9/10 below).
10. **Alert process**: `backend/dispatch_alerts.py` (Twilio SMS). **Phase 4 fix**: this step used to run *before* the canonical build/validation step — moved this phase to run *after* it, so alerts now fire only once the canonical artifact for this cycle has been built and passed schema+integrity validation. `dispatch_alerts.py` itself still reads `data/pan_india_grid.json` directly, not `canonical_forecast.json` (changing that would be redesigning the alert system, out of scope this phase).
11. **Upstream fetch failure**: `backend/pipeline.py::download_grib()` retries up to 3 times; if all fail, `main()` prints `"FATAL: could not download GFS data -- aborting"` and calls `sys.exit(1)`. The "Run pipeline" step has **no** `continue-on-error`, so the entire job stops there — no canonical build, no alert dispatch, no commit, no push. `data/pan_india_grid.json` is left completely untouched (last known good stays on disk and on `main`). This is the existing, correct behavior for GFS failure (see Part 3 below): a failed refresh cannot make a stale forecast look fresh, because nothing downstream of the failed fetch ever runs.

## `forecast_update.yml` (VOBL station forecast)

1. **Trigger**: 5 crons/day (slot-aligned + one extra evening run) + manual dispatch with an optional `slot` override.
2. **Source data fetched**: `gfs_fetcher.py` (VOBL-point GFS/upper-air, appends a row to `data/gfs_realtime_43295.csv`), `pan_india_gfs_fetcher.py` (writes its own `data/pan_india_grid_slotrun.json`, explicitly **not** the shared `data/pan_india_grid.json` — verified in `pan_india_gfs_fetcher.py`'s own header comment, corroborating `docs/PIPELINE_OWNERSHIP.md`), `fetch_himawari_realtime.py` (Himawari-9 Band 13 crop), `fetch_dem_terrain.py`, `fetch_metar.py`. All four fetch steps have `continue-on-error: true`.
3. **Source data timestamp**: `gfs_fetcher.py` writes `fetched_at_utc` per row into `data/gfs_realtime_43295.csv` — this is the one place in the repo with a real fetch-time field distinct from any forecast-validity time. `fetch_himawari_realtime.py` writes `timestamp_utc`/`timestamp_ist` (the satellite observation time) into `forecast.json`'s `satellite.himawari9` block (nested — see Phase 3.5's fix for the lookup bug this caused).
4. **Forecast files generated**: `forecast.json` (the VOBL document: 4 slots, Himawari, METAR, terrain, multiday outlook, SHAP, verification, alert log).
5. **Script generating each artifact**: `forecast_action.py` writes `forecast.json`. **Phase 4.5**: both the main write and the emergency-crash-handler write now go through `atomic_write_json()`. A real latent bug was found and fixed in the same change: `forecast_action.py` never imported `sys` anywhere in the file, so the crash handler's own `sys.exit(1)` would have raised `NameError` instead of exiting cleanly — `import sys` added. On an uncaught exception, the handler now atomically writes an "emergency" minimal degraded document, and if that write itself fails, the previous valid `forecast.json` is left untouched rather than partially overwritten (verified by reading the `try/except` around `main()` — `"FATAL: forecast_action.py crashed — writing emergency forecast.json"`).
6. **Canonical script**: `canonical_forecast_writer.py`, invoked right after "Run forecast pipeline" (Phase 3.5), now preceded by a "Sync latest cross-workflow artifacts" pull (Phase 4, Part 9).
7. **Validation**: same as above — schema + integrity inside the writer, before any write.
8. **Commit/push**: `git add forecast.json data/canonical_forecast.json data/gfs_realtime_43295.csv ...` (long list), commit, push with `--force-with-lease` fallback to plain push, then a rebase-retry block on failure.
9. **Cloudflare deployment**: `npx wrangler@3.87.0 pages deploy .` — deploys the **entire checked-out working directory** (`.`), which by this point in the job includes the just-written `forecast.json` and `data/canonical_forecast.json`, whatever `data/pan_india_grid.json` happened to be checked out at job start (see Part 9/10), and the `index.html` with the Worker URL freshly `sed`-injected.
10. **Alert process**: `send_alerts.py` (WhatsApp, real delivery-state tracking, see `docs/ALERT_SYSTEM_AUDIT.md`) and an optional ntfy.sh push notification (Phase 3.5-hardened, no more silent `|| true`). Both run *after* the canonical build step (Phase 4 sync step + canonical build were inserted before "Compute real-time SHAP", which itself is before "Send WhatsApp alerts") — so for this workflow, the required order (FETCH → FORECAST → CANONICAL → VALIDATE → PUBLISH-locally → ALERT) already held even before this phase's changes; nothing needed reordering here.
11. **Upstream fetch failure**: `gfs_fetcher.py`/`fetch_himawari_realtime.py`/`fetch_dem_terrain.py`/`fetch_metar.py` all have `continue-on-error: true` — a failure in any of them does **not** stop the job. `forecast_action.py` then runs regardless, and (traced directly in its own source) degrades gracefully **per slot**: if no valid GFS row exists for today, that slot's `source` becomes `"model_defaults"` (real trained model, climatological default inputs) or `"climatology"`/`"climatology_model_error"` (no trained model at all), each explicitly labeled with `fallback`/`fallback_reason`. `forecast_action.py` itself never exits non-zero on a data-availability problem — only a genuine code exception triggers the emergency-document fallback. **Phase 4.5**: "no valid GFS row exists for today" is no longer only a date-match check — `gfs_row_select.py::select_latest_gfs()` now also rejects the freshest candidate row if it is older than `GFS_MAX_AGE_HOURS` (see Part 3 below), so a GFS row fetched many hours ago but still calendar-dated "today" (e.g. fetched at 00:10 IST, evaluated at 23:00 IST the same day) is now correctly treated as no-valid-input rather than silently accepted as current. This surfaces through `forecast_action.py`'s existing `source`/`fallback` labeling unchanged.

## Phase 4.5: status of the items above, closed this phase

- **Atomic writes** — CLOSED. `backend/pipeline.py` (`pan_india_grid.json`, `ctt_grid.json`) and `forecast_action.py` (`forecast.json`, both the main and emergency-crash-handler writes) now all go through `atomic_write.py::atomic_write_json()`. Nothing else in either file was touched — diagnostic/log writes (`pipeline_health.json`'s crash record, print statements) were deliberately left as plain writes, since they are not part of the production forecast publication path and making every incidental write atomic would be over-engineering.
- **GFS max-age gate** — CLOSED. `gfs_row_select.py` now has `check_gfs_freshness()` (returns `VALID`/`STALE`/`INVALID`) and `GFS_MAX_AGE_HOURS = 7.0`, wired into `select_latest_gfs()`: the freshest otherwise-valid candidate row is rejected outright (not silently substituted with an older row) if it is stale or has an unparseable/future timestamp. See "GFS max-age rule" below for why 7.0 hours specifically.
- **Cross-workflow race** — MOSTLY CLOSED. See "Race-control design" below for the full analysis; a small residual window remains and is named explicitly, not hidden.

## Race-control design (Phase 4.5 Part 1)

**Mechanism used**: both `update_grid.yml` and `forecast_update.yml` now declare
```yaml
concurrency:
  group: sih-forecast-publish
  cancel-in-progress: false
```
GitHub Actions guarantees that at most one job across BOTH workflows in this shared group runs at a time; a second trigger while one is running is **queued**, not cancelled, and not run in parallel. This was chosen over `cancel-in-progress: true` deliberately: cancelling a running job mid-`backend/pipeline.py` (e.g. partway through GRIB parsing or the canonical build) would abort a forecast generation with no defined recovery state, and is exactly the kind of "confusing state" the task explicitly warned against. Queuing costs at most one run's worth of latency (roughly 2-6 minutes based on the existing step timings) and never aborts an in-flight publish.

**Why this actually closes the common race**: a queued job's own `actions/checkout` step does not run until the job actually starts — which, under this concurrency group, is only after the previously-running job (from either workflow) has fully finished, including its `git push`. So the queued job's checkout is guaranteed to include the other workflow's just-published commit. This is what "smallest deterministic solution, no sleep/retry loop" means here: GitHub's own scheduler is the ordering primitive, not a wait loop this repo would have to maintain.

**Defense in depth retained**: the Phase 4 "Sync latest cross-workflow artifacts" `git pull origin main --no-rebase` step immediately before each workflow's canonical build is kept. It is redundant with the concurrency group for the common two-different-workflows case, but still useful for: (a) two runs of the *same* workflow queuing back-to-back (e.g. a manual `workflow_dispatch` overlapping a scheduled run) where the concurrency group already serializes them but an explicit pull is cheap insurance, and (b) a small window right at a queued job's start where its checkout could theoretically be from a commit slightly behind `origin/main`'s absolute latest if GitHub's internal state propagation lags by a few seconds — the pull step re-syncs before the canonical build reads its inputs.

**What this does NOT fully close**: a genuinely simultaneous `workflow_dispatch` of both workflows at the exact same instant could still both be admitted to the queue in an order GitHub decides, not this repo — but critically, they can never *run concurrently* once queued, so the second one to actually execute always sees the first one's push. The scenario the task described (`push can still occur between another workflow's pull and push`) is the one this concurrency group eliminates: that scenario requires two jobs' steps interleaving in real time, which the shared group makes structurally impossible. The one theoretical residual case documented here for completeness: if GitHub's `main` branch protection or push propagation itself has a delay longer than the interval between one job ending and the next queued job's checkout starting (not observed in this repo's history, and not something this repo can control), a queued job's checkout could technically be a moment behind — this is a GitHub-infrastructure-level concern, not a fix this codebase can add.

**Workflow ownership verification**: `tests/test_phase45_reliability.py::test_6_workflow_concurrency_configured` asserts both workflow files declare the shared group with `cancel-in-progress: false`, so a future edit that silently drops or diverges the group name would fail CI's local test run (were these tests wired into CI — they currently run via manual/local invocation only, as with all other `tests/` files in this repo).

## GFS max-age rule (Phase 4.5 Part 3)

`gfs_row_select.py::GFS_MAX_AGE_HOURS = 7.0`, enforced by `check_gfs_freshness()` inside `select_latest_gfs()`.

**Why 7.0 hours, not an arbitrary number**: GFS posts a new cycle every 6 hours (00/06/12/18Z), and both production workflows (`update_grid.yml`'s cron, `forecast_update.yml`'s slot crons) are scheduled on that same ~6-hourly cadence. A GFS row whose `fetched_at_utc` is more than one full cycle old was fetched before the *current* cycle would even be expected to have posted — it necessarily reflects the previous cycle's data being reused past its intended window. The extra 1 hour on top of the 6-hour cycle is the same scheduling-jitter buffer already used and documented for `canonical_forecast_writer.py::GFS_STALE_AFTER_HOURS` (Phase 3.5) — this phase intentionally reused that exact number rather than inventing a second, potentially-diverging one; both constants are cross-referenced in comments in each file so a future change to one is a visible signal to check the other.

**VALID / STALE / INVALID**, from `check_gfs_freshness()`:
- `VALID` — `fetched_at_utc` present, parseable, and within `GFS_MAX_AGE_HOURS` of the evaluation time (with a 10-minute forward-clock-skew allowance).
- `STALE` — present and parseable, but older than the threshold.
- `INVALID` — missing, unparseable, or further in the future than the clock-skew allowance (a "fresher than now" timestamp is untrustworthy, not extra-fresh).

**No silent substitution**: `select_latest_gfs()` only evaluates the single freshest otherwise-valid (finite CAPE/K_INDEX) candidate row. If that row is `STALE` or `INVALID`, the function returns `None` immediately — it does not fall back to the next-newest row in the sorted list. An older row is never a legitimate substitute for "today's current cycle wasn't fetched in time"; the existing caller (`forecast_action.py`) already treats a `None` selection as "no valid GFS input for today" and degrades to its own explicitly-labeled climatology fallback, so no caller behavior needed to change.

## Failure-scenario trace (Phase 4.5 Part 5)

| Scenario | Traced behavior |
|---|---|
| A. GFS fetch succeeds → forecast → canonical → publish all succeed | Normal path: `backend/pipeline.py`/`forecast_action.py` write atomically, `canonical_forecast_writer.py` schema+integrity validates then atomically publishes, commit/push/deploy proceed. |
| B. GFS fetch fails | `backend/pipeline.py::download_grib()` exhausts 3 retries → `sys.exit(1)` → `update_grid.yml`'s "Run pipeline" step (no `continue-on-error`) stops the entire job. No canonical build, no alert, no commit, no push. Previous `pan_india_grid.json`/`canonical_forecast.json` on `main` are untouched. |
| C. GFS fetch succeeds but the selected row is too old | **Phase 4.5**: `select_latest_gfs()` now rejects the freshest candidate as `STALE` per `check_gfs_freshness()` and returns `None`. `forecast_action.py`'s existing caller logic treats this exactly like "no valid row" — that slot's `source` becomes `"model_defaults"`/`"climatology"`, explicitly labeled, and `forecast_action.py` still writes a (degraded, honestly-labeled) `forecast.json` rather than crashing; the *pan-India* path (`backend/pipeline.py`) has no equivalent per-row staleness concept since it downloads one fresh GRIB per run rather than accumulating a CSV of rows, so this scenario is VOBL-specific. |
| D. Himawari fails | All Himawari fetch steps have `continue-on-error: true`; `fetch_himawari_realtime.py`'s own S3→JAXA→10-min-earlier-slot fallback chain, and on total failure writes a placeholder with `data_source: "...UNAVAILABLE..."`. **Phase 3.5/4 fix retained**: `canonical_forecast_writer.py` independently checks `vobl_bt_celsius is not None` and the `data_source` string (not `forecast_action.py`'s own buggy `bool(dict)` check) to report `himawari.status: FAILED` rather than a fake-available state; no CTT-drop-rate or CTT-tendency computation is attempted when Himawari data is unavailable/stale. GFS-based (VOBL XGBoost + pan-India physics-proxy) forecasting continues independently, per the existing design. |
| E. Forecast engine crashes while writing output | **Phase 4.5**: both `forecast_action.py`'s main write and its emergency-crash-handler write now go through `atomic_write_json()`. If the crash happens before either write starts, the previous valid `forecast.json` is untouched by construction (atomic writer never touches the destination until the new content is fully flushed+fsynced). If the emergency handler's OWN write also fails (e.g. disk full), it is caught and logged, and the previous valid `forecast.json` is still left untouched — this exact scenario is covered by `tests/test_phase45_reliability.py::test_2_atomic_write_preserves_previous_on_failure`. |
| F. Canonical validation fails | `canonical_forecast_writer.py::main()` calls `validate_schema()`/`validate_integrity()` BEFORE any write; either failing prints the errors and returns 1 without ever calling `atomic_write_json()`. The step has no `continue-on-error` in either workflow, so the job stops there — the commit/push and (in `forecast_update.yml`) Cloudflare deploy steps never run. |
| G. Two workflows trigger close together | See "Race-control design" above: the shared `concurrency: sih-forecast-publish` group with `cancel-in-progress: false` means the second trigger queues rather than runs concurrently, so its checkout (once it starts) always includes the first's push. |
