# Phase 0.4.8 — VOBL Historical GFS → Thunderstorm Supervised Join Report

This phase builds the smallest real, fully auditable historical GFS →
VOBL observed-thunderstorm supervised-join table. It does not train a
model, does not download any additional data, does not modify production
inference, and does not deploy, commit, or push. Everything in this report
is generated by actually running
`scripts/build_vobl_historical_gfs_ts_join.py` against the two
already-downloaded GRIB2 files, and by actually running the new test
suite (`tests/test_vobl_historical_gfs_ts_join.py`).

**Important finding, not glossed over**: both 08:30 IST and 11:30 IST fall

observed-TS label row (`2020-07-15T0601-1200`). This is a direct
consequence of only having one 00Z cycle with leads 3h and 6h on hand —
it is not a bug in the join logic, but it does mean this specific
two-row pilot cannot demonstrate two *different* label outcomes, only two
different forecasts pointed at the same outcome. This is stated
explicitly rather than left for a reader to discover.

## 15. Leakage checks

Every feature in this pilot is classified `FORECAST_DERIVED`: a value
produced by the GFS model's physics integration at the stated
`initialization_time`, describing a condition valid at a **later**
(`valid_time_utc`) moment — not an observation made after initialization
and fed back in as a predictor. No feature is classified
`USES_FUTURE_INFORMATION`, verified programmatically
(`manifest["features_using_future_information"] == []`, test
`test_h_no_feature_uses_future_information`).

For `gfs_precip_3h_interval_mm` specifically: it is `tp(f006) - tp(f003)`,
the forecast model's own accumulated-precipitation field differenced
across two leads of the **same** initialization cycle (confirmed by
`verify_same_initialization_cycle`). Both `tp` fields are themselves
forecast outputs computed at initialization time describing future
accumulation — not observed/gauge rainfall. This differencing was only
performed after confirming (reused from Phase 0.4.4/0.4.5, not
re-litigated) that both accumulation windows share `startStep=0`.

**Honest limitation, stated explicitly**: this interval feature
represents the 3h→6h accumulation window, not a 0h→3h window, because
this pilot has no lead-0 (`f000`) file. It is therefore attached only to
the lead-6h row; the lead-3h row's `gfs_precip_3h_interval_mm` is left
null with an explicit note
(`"not computable from this pilot: no lead-0 tp field available to form a
0-3h interval (only f003 and f006 downloaded)"`) rather than approximated
or silently backfilled from the other row.

Temporal ordering was checked for every row:
`initialization_time_utc < valid_time_utc` holds for both rows (3h and 6h
ahead respectively), and `forecast_lead_hours` was independently
recomputed as `(valid_time − initialization_time)` and compared against
the GRIB-reported lead — they match exactly for both rows (verified by
test `test_i_lead_hours_match_valid_minus_init`). This confirms the
dataset is structured as forecast-at-initialization → later-valid-time
predictor, joined to a label observed at (or after) that same later valid
time — not forecast → same-initialization-time observation.

## Does this dataset represent a genuine future-forecast → observed-thunderstorm supervised learning problem?

**YES**, with one honestly-stated caveat.

Justification from the actual rows:

- Both rows' predictors are GFS model forecast fields computed entirely
  from data available at `initialization_time_utc = 2020-07-15 00:00
  UTC`, describing atmospheric state at a **strictly later**
  `valid_time_utc` (03:00 UTC / 06:00 UTC respectively) — confirmed
  `initialization_time < valid_time` for both rows, with an
  independently recomputed lead time matching the GRIB-reported lead
  exactly.
- The label each row joins to (`label_status = NEGATIVE_CONFIRMED` at
  `2020-07-15T0601-1200`, VOBL) is a real station observation made during
  (and only finalized at the close of) that IST slot window — a window
  that starts at or after each row's own `valid_time_ist`, never before
  it. No feature classifies as `USES_FUTURE_INFORMATION`.
- The join uses the project's own already-established canonical cell
  (`IND_13.0_78.0`), slot table (`lead_time.SLOT_WINDOWS_IST`), and label
  file (`ts_labels.csv`) without modification, re-derivation, or
  fabrication of any value.

The caveat: because this specific 00Z/2020-07-15 cycle's two available
leads (3h, 6h) both fall inside the *same* 6-hour IST label slot, this
two-row pilot demonstrates the **mechanics** of a genuine
forecast-to-later-observation join (different predictor snapshots at
different leads, correctly time-ordered, correctly joined to a real
future-relative label) but does not yet demonstrate the join producing
**two different label outcomes** from **two different initialization
cycles** — that would require at least one additional cycle (ideally one
landing on a day VOBL's real labels show a confirmed positive), which
this phase deliberately does not acquire, per the stop condition in
Section 18.

## 18. Stop condition check

The existing two GFS files **did** produce a scientifically valid joined

negatives, 0 unmatched.
