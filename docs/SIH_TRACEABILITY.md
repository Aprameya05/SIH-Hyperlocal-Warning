# SIH26077 traceability audit (code and artifacts as of origin/main `2549c61`)

This audit maps each SIH26077 requirement to what the code and committed artifacts actually do. It is skeptical by design: a module that exists but is not called from a production workflow, or a model that has no evaluation artifact, does not count as implemented.

- **Scope:** clean checkout of `origin/main` at `2549c61`. Artifacts were read on 2026-11-23, from the bot cycle that produced `data/*.json` at 2026-11-23 ~04:00-05:00 UTC.
- **Method:** I read the source files, read `.github/workflows/*.yml` to see what really runs, and ran small read-only Python checks on `data/*.json`, `models/*.json` and one training CSV. Nothing was downloaded, retrained or deployed.
- **Relationship to `docs/FINAL_SIH_REQUIREMENT_TRACEABILITY.md`:** this document supersedes it where the two disagree. That file marks "Explainability" and "Dashboard" as MET without the caveats listed below.

## 0. Verification log and status after the engineering PRs

Re-checked independently against source and data on 2026-11-23 (all confirmed unless noted): `backend/fetch_insat3d.py` is not referenced by any workflow or pipeline; `himawari_correction_model` is referenced only by `train_correction_model.py` and `research/legacy_experiments/`; `data/drainage.geojson` does not exist; `data/unified_forecast.json` `init_time_utc` is `2024-08-01T00:00:00Z`; `conv850`/`conv10` are computed at ingest but the 24 pan-India TS features contain no convergence term; `backend/pipeline.py` labels `qpe_*` a "QPE PROXY"; the station CB label leakage (99.4% of 15,276 rows); the 19 never-live station features. **Corrected:** `bt_trend_1h` is null in 5 of 6 frames, not all 6.

## 5. Top 10 actionable issues

1. **Station CB/FF models leak the target.** The same-day observed `RF` is a feature, and `cb_label == (RF >= 64.5)` in 99.4% of rows; only 60 positive rows exist. At inference `RF` is hardcoded 0. Retire `models/cb_slot_*`/`ff_slot_*` and the `hazard_summary` they feed in `forecast.json`, or retrain them without `RF`/`DRNRF`/`RF_3d`/`RF_lag1` and with event-level splits.
2. **`drift_check.yml` deploys the whole repo (`pages deploy .`).** This bypasses the Pages bundle deny-list and can publish `data/subscribers.json`, the `*.db` files and the models. Switch it to `build_pages_bundle.py` output, and remove the force-push to `main`.
3. **There is no 2-6 h lead.** Record `forecast_available_time_utc` (the bundle publish time; GFS `published_at`/`acquired_at` are already logged) and add 3-hourly fhours from the 06Z/18Z cycles so that leads fall inside +2..+6 h. Without this, no hazard can ever become alert-eligible.
4. **The station models run on hardcoded climatological inputs** (`forecast_action.py` L512-529). Pass NaN (XGBoost handles missing values) or real IMD station observations, and stop SHAP from "explaining" defaults (e.g. `MIN_3d_avg = 20.0` shown as a driver).
5. **"Cloudburst" is a heavy-rain-day proxy** (IMD >= 64.5 mm/day, 10 training dates, daily aggregate). Rename it in the UI and API everywhere to "heavy-rain day", and start an hourly cloudburst label set (IMD AWS/ARG hourly) before claiming cloudburst prediction.
6. **Flash flood has no trained dynamic model.** Only a PU ranking on static catchment attributes, a DEM susceptibility proxy and a hand-weighted browser heuristic exist. Acquire ERA5 for INDOFLOODS event dates and matched negatives, as `flash_flood_v2` README proposes, then train and evaluate. Also mask the DEM proxy over the ocean (299 sea cells currently get 0.775).
7. **The legacy 1-deg heuristic grid is still published** as `*_probability` (`backend/pipeline.py hazard_probabilities`, `pan_india_grid.json`, root `index.html`), and its `cloudburst_probability` mixes heuristic and model semantics. Retire it, or rename the keys to `*_heuristic_score`, and make `drift.html` the site root.
8. **No satellite data enters any model.** Himawari is VOBL-only B13 BT for display; the cooling rate is null in 5 of 6 history frames; INSAT is not wired. Fix `bt_trend_1h`, grid B13 pan-India, and add BT and cooling rate to the TS/rain feature sets, gated on the existing evaluation gate.
9. **The pan-India TS model was trained only on Apr-Jun** and runs year-round, with no live verification. Add monsoon and post-monsoon training dates, and a daily verification job against the 113-station METAR feed. `skill_scores.json` currently verifies only VOBL and has had no events in 30 days.
10. **Stale claims in artifacts and docs.** `build_live_feed.py` hardcodes "No pan-India thunderstorm probability exists"; `qpe_*` columns are GFS APCP, not satellite QPE; the CB outlook says UNCALIBRATED but is isotonic-stepped; `FINAL_SIH_REQUIREMENT_TRACEABILITY.md` marks Explainability and Dashboard MET. Correct these labels, and either deploy the FastAPI service or stop describing it as the production API.
