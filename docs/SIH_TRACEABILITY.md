# SIH26077 traceability audit (code and artifacts as of origin/main `2549c61`; fully re-verified at `43d85e9`)

This audit maps each SIH26077 requirement to what the code and committed artifacts actually do. It is skeptical by design: a module that exists but is not called from a production workflow, or a model that has no evaluation artifact, does not count as implemented.

- **Scope:** first written against a clean checkout of `origin/main` at `2549c61`, then re-verified row by row against `origin/main` at `43d85e9` (after PRs #2-#12). Artifacts were read on 2026-11-23. The committed `data/*.json` and `forecast.json` come from the bot cycles of 2026-11-23 ~02:57-04:58 UTC (`f46aedd` and earlier). They were **not regenerated** after PRs #7-#9 merged, so they still show pre-fix behaviour in places. Where that matters, the row says so.
- **Method:** I read the source files, read `.github/workflows/*.yml` to see what really runs, and ran small read-only Python checks on `data/*.json`, `models/*.json` and one training CSV. Nothing was downloaded, retrained or deployed.
- **Relationship to `docs/FINAL_SIH_REQUIREMENT_TRACEABILITY.md`:** this document supersedes it where the two disagree. That file marks "Explainability" and "Dashboard" as MET without the caveats listed below.

1. **Station CB/FF models leak the target.** The same-day observed `RF` is a feature, `cb_label == (RF >= 64.5)` holds in 99.4% of rows, and only 60 positive rows exist. **Mitigated by PR #8:** the scores are withheld (`hazard_summary.*.status: UNAVAILABLE`). Still to do: retire `models/cb_slot_*`/`ff_slot_*`, or retrain them without `RF`/`DRNRF`/`RF_3d`/`RF_lag1` and with event-level splits.
2. **(Resolved by PR #5.)** `drift_check.yml` no longer deploys the repo root or force-pushes. Remaining: it still posts to the public ntfy topic. Separately, `send_alerts.py` sends daily WhatsApp digests without the alert-policy gate (row 26). Decide whether digests should be gated.
3. **There is no 2-6 h lead.** Record `forecast_available_time_utc` (the bundle publish time; GFS `published_at`/`acquired_at` are already logged). Train TS leads at +3/+9 h on the 3-hourly fhours that are already ingested (the rain +9 h target already falls about 4 h after acquisition). Without this, no hazard can ever become alert-eligible.
4. **The station models run on hardcoded climatological inputs** (`forecast_action.py` L511-530; 28 of 64 (20 station observations + 8 never-computed features) features). **Mitigated by PR #7:** every slot is flagged fallback and the constants are excluded from SHAP. As a result no station slot can raise an alert, except through the METAR override (L1285-1300), which bypasses that gating. Next: pass NaN (XGBoost handles missing values) or real IMD station observations, then retrain.
5. **"Cloudburst" is a heavy-rain-day proxy** (IMD >= 64.5 mm/day, 10 training dates, daily aggregate), and its published value is calibrated while labelled UNCALIBRATED. Rename it to "heavy-rain day" everywhere in the UI and API, fix `forecast_integrity.py` L360, and start an hourly cloudburst label set (IMD AWS/ARG hourly) before claiming cloudburst prediction.
6. **Flash flood has no trained dynamic model.** Only a PU ranking on static catchment attributes, a DEM susceptibility proxy and a hand-weighted browser heuristic exist. Acquire ERA5 for INDOFLOODS event dates and matched negatives, as the `flash_flood_v2` README proposes, then train and evaluate. Also mask the DEM proxy over the ocean (299 sea cells currently get 0.775).
7. **The legacy 1-deg heuristic grid is still published** as `*_probability` (`backend/pipeline.py hazard_probabilities`, `pan_india_grid.json`, root `index.html`), and its `cloudburst_probability` mixes heuristic and model semantics. Retire it, or rename the keys to `*_heuristic_score`, and make `drift.html` the site root. Also fix the TS-model layer's lead indexing in `drift_app.js` L79.
8. **No satellite data enters any model.** Himawari is VOBL-only B13 BT for display. The cooling rate is null in 5 of 6 history frames because frames are fetched hours apart (the 75-min gap rule then returns null). INSAT is not wired. Fetch B13 at 10-30 min cadence, grid it pan-India, and add BT and cooling rate to the TS/rain feature sets, gated on the existing evaluation gate.
9. **The pan-India TS model was trained only on Apr-Jun** and runs year-round, with no live verification. Add monsoon and post-monsoon training dates and a daily verification job against the 113-station METAR feed. `skill_scores.json` currently verifies only VOBL and has had no events in 30 days.
10. **Stale claims in artifacts and docs.** These are still open: `qpe_*` columns are GFS APCP, not satellite QPE; the CB outlook says UNCALIBRATED but is calibrated; `summarise_baseline_evaluations.py` L54 says no pan-India TS model is validated, and L64 says "6 informative" CB dates; `FINAL_SIH_REQUIREMENT_TRACEABILITY.md` marks Explainability and Dashboard MET. `build_live_feed.py` is fixed in code (PR #9). The committed `drift_live.json`, `forecast.json` and `realtime_shap.json` predate PRs #7-#9 and need a successful production run to refresh. Correct the remaining labels, and either deploy the FastAPI service or stop describing it as the production API.
